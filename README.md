# SaaS Customer Health Intelligence

An end-to-end churn-risk detection system, built from scratch on synthetic SaaS data: PostgreSQL for the analytical pipeline, Python for data generation, Power BI for delivery.

![Dashboard](dashboard/dashboard_screenshot.png)

## Overview

**Summary.** A customer health scoring system for a 2,000-customer synthetic SaaS company. Usage-engagement trends and payment-health signals are combined into a single, explainable risk tier per customer, surfaced through a Power BI dashboard designed to be read in under 90 seconds.

**Problem statement.** Which customers are at risk of churning right now, how much revenue is that worth, and why is it happening — so Customer Success knows exactly who to call today, not who churned last quarter.

## Key results

- **Total active MRR:** $316.0K
- **MRR at risk (At-Risk + Watch):** $46.3K (14.6%)
- **At-Risk customers:** 5
- **Watch customers:** 195
- **Ground-truth recall on true decliners:** 43.5%
- **False-positive rate, worst segment:** 7.3% (down from 47% pre-redesign)

## Data

**Data provenance.** All data is synthetic, generated by `python/01_data_generation.ipynb`. No external dataset is used — customers, subscriptions, usage events, payments, and hidden "true" churn-behavior personas are all procedurally generated with realistic distributions and deliberate data-quality corruption.

**Data dictionary — `final_output` (dashboard source table)**

| Column           | Type    | Description                                                                 |
|:-----------------|:--------|:----------------------------------------------------------------------------|
| `customer_id`    | int     | Unique customer identifier                                                   |
| `mrr`            | decimal | Monthly recurring revenue                                                    |
| `risk_tier`      | text    | At-Risk / Watch / Healthy / Churned / Insufficient Data                     |
| `trend_direction`| text    | Worsening / Dormant / Sustained / Improving / Insufficient Data            |
| `payment_flag`   | int     | 1 if payment overdue beyond billing-cycle grace period, else 0             |
| `reason`         | text    | Plain-English explanation of the tier assignment                            |

**Missing / corrupted data.** The generator deliberately injects five categories of data-quality issues into `usage_events` (missing feature values, duplicate rows, orphan customer IDs, session-count outliers, post-cancellation activity) and three into `payments` (duplicate transactions, zero-amount successes, inconsistent status casing), used as cleaning practice in `01_data_understanding.sql` and `02_data_cleaning.sql`.

## Workflow

**Code structure:**
```
sql/
  01_data_understanding.sql
  02_data_cleaning.sql
  03_kpi_definitions.sql
  04_engagement_metrics.sql     gap & island streak logic
  05_trend_analysis.sql         date-spine + gap-per-checkpoint scaffold
  06_payments_signal.sql        payment failure rate & flag, billing-cycle aware
  07_risk_tiering.sql           trend + payment combined — source of truth
  08_output_table.sql           final output, reads from 07

python/
  01_data_generation.ipynb      synthetic data generator

dashboard/
  saas_health_dashboard.pbix
  dashboard_screenshot.png
```

**Data transformation.** Trend is derived from a per-customer gap-over-time timeline, not a single snapshot: customers are first routed by behavior shape (a sparsity score separating continuous-activity from cyclical-activity customers), then scored with the trend logic appropriate to that shape — simple recent-delta averaging for continuous customers, lifetime peak-to-peak slope for cyclical ones. Payment health is scored independently, on a threshold relative to each customer's own billing cycle. The two signals combine into one risk tier in `07_risk_tiering.sql`, a materialized table that is the single source of truth for tier logic; `08_output_table.sql` reads from it and adds a plain-English `reason` column rather than recomputing anything.

**Execution steps:**
1. Run `python/01_data_generation.ipynb` top to bottom (fresh kernel) to populate `customers`, `subscriptions`, `usage_events`, `payments`, `customer_personas`.
2. Run `sql/01` through `sql/08` in order in PostgreSQL.
3. Open `dashboard/saas_health_dashboard.pbix` in Power BI Desktop, point the PostgreSQL connection at your local database, refresh.

## Insights

![Dashboard](dashboard/dashboard_screenshot.png)

**Executive summary:**
- Usage decline is the dominant risk driver — usage-related reasons account for roughly 3x more at-risk MRR than payment issues alone.
- The 5 At-Risk customers show both declining usage **and** payment failure simultaneously — the highest-severity, compounding case, and the correct first call for Customer Success.
- A behavior-aware trend classifier cut the false-positive rate on erratic, healthy customers from 47% to 7.3%, at the cost of only a modest gain in recall on genuine decliners (38% → 43.5%) — a real, disclosed tradeoff, not a fully solved problem.

## Recommendations & future work

**Actionable recommendation.** Prioritize outreach to the 5 At-Risk customers first — they represent the highest-severity, compounding-risk case — followed by Watch customers filtered by `reason` to distinguish usage-driven risk from payment-driven risk, since each needs a different conversation.

**Limitations.**
- Recall on genuine decliners caps at ~43.5% with the current classifier; more than half of true decliners are not yet flagged. Root cause is understood (see below) but not resolved.
- The dataset is a static snapshot (as of 2026-02-04), not a live feed — the dashboard does not reflect real-time changes.
- Ground-truth validation is only possible because this is synthetic data with hidden true labels; a production deployment would need a different validation approach (e.g., backtesting against actual churn events).

**Future scope.**
- Redesign the trend label from a fixed three-way category into a continuous slope value, since forcing categorical certainty onto cyclical decline-with-recovery behavior is the main source of the current recall ceiling.
- Add cohort-level slicing (plan tier, signup cohort, region) once those dimensions are exposed in the dashboard model.
- Replace the static snapshot with a recurring extract (even weekly) to enable a genuine trend-over-time view in Power BI itself.
